### Class and Method-Level @Transactional Annotation with Precedence

Source: https://github.com/spring-projects/spring-framework/blob/v7.0.5/framework-docs/modules/ROOT/pages/data-access/transaction/declarative/annotations.adoc

Demonstrates @Transactional annotation applied at both class and method levels, showing how method-level settings override class-level settings. The class is marked as read-only, but the updateFoo method overrides this with read-write and REQUIRES_NEW propagation. This pattern is essential for fine-grained transaction control in Spring applications.

```java
@Transactional(readOnly = true)
public class DefaultFooService implements FooService {

	public Foo getFoo(String fooName) {
		// ...
	}

	// these settings have precedence for this method
	@Transactional(readOnly = false, propagation = Propagation.REQUIRES_NEW)
	public void updateFoo(Foo foo) {
		// ...
	}
}
```

### Rolling Back a Declarative Transaction > Rollback Rules > Configuration

Source: https://github.com/spring-projects/spring-framework/blob/v7.0.5/framework-docs/modules/ROOT/pages/data-access/transaction/declarative/rolling-back.adoc

Rollback rules determine if a transaction should be rolled back when a given exception is thrown, and the rules are based on exception types or exception patterns. Rollback rules may be configured in XML via the `rollback-for` and `no-rollback-for` attributes, which allow rules to be defined as patterns. When using `@Transactional`, rollback rules may be configured via the `rollbackFor`/`noRollbackFor` and `rollbackForClassName`/`noRollbackForClassName` attributes, which allow rules to be defined based on exception types or patterns, respectively.

### Transaction Management > Rollback Rules > Declarative Configuration

Source: https://github.com/spring-projects/spring-framework/blob/v7.0.5/framework-docs/modules/ROOT/pages/data-access/transaction/declarative/rolling-back.adoc

Spring Framework's transaction infrastructure supports both rollback and no-rollback rules through the `rollback-for` and `no-rollback-for` attributes in transaction advice configuration. The `rollback-for` attribute specifies exception patterns that should trigger a transaction rollback, while `no-rollback-for` specifies exceptions that should not cause rollback even if thrown. When multiple rules apply to an exception, the strongest matching rule wins, allowing you to define broad rollback rules with specific exceptions excluded from rollback.

### @Transactional Settings > Default Configuration

Source: https://github.com/spring-projects/spring-framework/blob/v7.0.5/framework-docs/modules/ROOT/pages/data-access/transaction/declarative/annotations.adoc

The `@Transactional` annotation is metadata that specifies that an interface, class, or method must have transactional semantics. The default `@Transactional` settings include: propagation setting of `PROPAGATION_REQUIRED`, isolation level of `ISOLATION_DEFAULT`, read-write transaction mode, transaction timeout defaulting to the underlying transaction system's default, and rollback triggered by any `RuntimeException` or `Error` while checked `Exception` does not trigger rollback.

### Understanding the Spring Framework Transaction Abstraction > TransactionDefinition

Source: https://github.com/spring-projects/spring-framework/blob/v7.0.5/framework-docs/modules/ROOT/pages/data-access/transaction/strategies.adoc

The `TransactionDefinition` interface specifies several key properties for a transaction: * Propagation: Defines the behavior if a transactional method is run when a transaction context already exists. Options include continuing in the existing transaction or suspending it to create a new one. Spring offers all transaction propagation options familiar from EJB CMT. * Isolation: Determines the degree to which this transaction is isolated from other transactions, such as whether it can see uncommitted writes. * Timeout: Sets the maximum duration before the transaction times out and is automatically rolled back by the underlying infrastructure. * Read-only status: Allows for optimization when the code only reads data and does not modify it, which can be useful in cases like Hibernate.
